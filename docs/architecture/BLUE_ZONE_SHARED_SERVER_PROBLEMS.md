# 蓝区多人共享开发服务器：现状问题与案例汇总

创建日期：2026-11-11。状态：第一版，供不同会话的 Agent 持续补充。

## 1. 目的与使用范围

本文汇总在缺少统一任务提交、资源调度、环境记录和产物管理时，多人使用蓝区服务器进行 Triton-Ascend / AscendNPU-IR 开发遇到的问题，为后续需求讨论和验收用例提供依据。

当前已知使用方式主要是：用户进入各自 Docker，管理工具链并直接执行命令。用户估计约有 100 人具有访问权限，峰值同时使用约 20 人；这是会话提供的规模估计，不是本次统计结果。

本文不是当前调度器的功能清单，也不表示下述问题都已解决。不要求通过 AI 解决所有问题：资源约束、权限和状态恢复需要确定性的程序与系统机制；Agent 可辅助理解任务、准备参数和分析证据。

证据标记：

- **[用户反馈]**：用户在本会话描述的需求、现象或管理员转述，未必已有独立复核。
- **[历史记录]**：已有工程记忆、实验记录或项目文档支持；历史状态不代表设备、环境目前仍相同。
- **[待核实风险]**：由现有使用方式推导的风险，不能写成已经发生的事故。

本次整理只读取文档，没有进行服务器资源普查、Docker/NPU 查询或新实验。其他会话的原始内容并非天然可见，后续请由持有记录的 Agent 补充。

## 3. 问题展开

### P01：NPU 分配靠人工协调，没有统一的等待队列

**[用户反馈]** NPU 卡数量有限，希望运行前自动选卡，容量满时进入等待队列。目前各人在自己的 Docker 内发起任务，缺少统一提交入口。

- 人工选卡难以持续掌握其他用户刚提交、正在初始化或尚未结束的任务。
- **[待核实风险]** 两个人都看到“空闲”后同时启动；一个长任务持续占卡，其他人只能反复检查或私下协调。
- 需要区分“观测到有人使用”和“已获得调度器分配”：前者不能阻止另一个用户直接执行命令。
- 待补充：真实抢卡时间线、物理卡编号、任务类型、双方受影响情况；不要为了补案例重新制造冲突。

### P02：共享资源不止 NPU，单独选卡不能保证任务可运行

**[用户反馈]** Docker 共享内存有限，用户也不确定还有哪些资源需要管理。**[历史记录]** 既有构建和采集任务涉及较高 CPU、内存、SHM 和产物存储需求。

- 编译 Triton、LLVM、NPU-IR 的 CPU 和内存需求，与算子性能测试、仿真采集的需求不同；编译任务也不一定需要 NPU。
- SHM、普通内存、工作盘、缓存、磁盘 inode、进程/线程数量和采集工具互斥等均可能构成瓶颈；具体共享范围取决于挂载、IPC 命名空间及 cgroup 配置，不能一律当成整机共享或每容器独享。
- 共享内存实际消耗还可能计入内存限制，不能将两个额度当成互不相关的可用资源。
- **[历史记录]** 2026-10-19 的编译复测涉及共享内存清理和临时容量调整，说明执行条件并非只有工具版本。该处置是历史个案，不构成扩大共享 SHM 的通用建议。
- **[待核实风险]** 多人同时高并发编译、产物写满磁盘或 PID 耗尽，导致没有参与这些任务的人也无法正常使用服务器。

### P03：性能数据缺少可比的测量条件

**[历史记录]** 相同 ELF 在不同设备和频率背景下曾出现显著耗时差异；PMU 采集也出现过需要核实计数一致性的现象。

- 性能不只依赖算子源码，还依赖物理卡、频率、健康状态、运行时、并发负载、预热和测量方式。
- 2026-10-26 的 MergeTopK 排查中，同一 ELF 在物理卡 0 当时约 100 MHz 时为 563.0342 μs，在物理卡 1 当时约 1650 MHz 时为 33.5670 μs。这是当时的对照，不能当成两张卡永久性能或健康结论。
- 2026-11-05 的 PMU 分析发现部分非 Pipe 请求窗口呈现 Pipe 多槽计数特征；当时无法确认是否有同卡其他 profiler，也没有事件选择寄存器读回证据，根因未定。不能将其写成“已证实其他用户污染采集”。
- 缺少并发背景和原始样本时，难区分真实编译器优化、设备状态变化、测量波动和采集异常。

### P04：设备可见不等于设备可用，编号和健康也需要单独记录

**[历史记录]** 已出现容器任务缺少设备补充组、受限任务访问设备返回 EBUSY，以及管理查询超时等情况。

- 宿主机物理编号、容器可见设备和运行时逻辑编号可能不同；只记录“device 0”不足以复现。
- 管理接口可查询、设备文件可打开、ACL/运行时可初始化、实际算子可正确执行，是不同层次的事实。
- 设备告警、低频或初始化失败可能与工具链问题表现相似，缺少运行前后证据时容易误判。
- **[待核实风险]** 仅依据旧健康截图或利用率为零分配设备；失败后自动改权限、反复探测或重启，扩大影响。
- 真实逐卡精度/性能资格仍需验证，不能用管理查询成功或固定微用例替代任意算子的正确性保证。

### P05：环境分散管理，源码、wheel 和实际执行工具可能不是同一版本

**[用户反馈]** 每次运行要确认 triton-ascend、bishengir 等版本，各自在 Docker 中维护，版本管理困难。

- 同一容器可能有多个 Conda/venv、源码 checkout、构建目录和安装目录；仓库 HEAD 不等于 Python 实际导入版本，也不等于后端实际调用的工具。
- 环境变量、外部工具路径、CANN、驱动、构建选项及未提交补丁都可能影响结果，仅记录包版本号不够。
- **[历史记录]** 2026-10-27 纯 SIMT 行号排查需要确认实际加载的 compiler.py 和工具链；其他路径已有修复不代表当前入口具备相同能力。
- **[历史记录]** LLVM 19/22 组合涉及 IR 接口和 bytecode 兼容边界；HiF8 构建也曾被历史手动编译宏掩盖配置传递缺口。不能把某个构建成功直接推广到另一套环境。
- **[待核实风险]** 在公用安装目录修改代码而没有备份和指纹，导致其他用户的后续结果悄然变化。

### P06：命令繁杂，任务意图没有形成可复用的执行说明

**[用户反馈]** 常见任务集中在精度、性能、仿真、编译和 IR 开发，但每类任务仍要手工准备命令、环境和输出路径。

- 运行常涉及环境激活、可见卡、编译器路径、dump、缓存、超时、工作目录及 profiler 参数，多处参数需要保持一致。
- 精度、性能和仿真应有不同的执行规模；复制旧命令可能带入 autotune、全量 pytest、旧输入或重复采样。
- **[历史记录]** causal conv 曾需要另做一次 kernel 启动的入口，避开 autotune/profiler 循环；历史 simulate.sh 同时保留多条旧命令，不适合直接整文件执行。
- **[待核实风险]** Agent 只看“运行测试”就启动整套测试，或构建脚本默认使用过多并发；命令执行成功也未必完成用户真正想做的检查。
- 新用户需要反复向同事询问，一次性的正确命令很难成为团队可追溯的任务规范。

### P07：产物路径分散，结果与其来源容易脱节

**[用户反馈]** IR dump 路径很长，性能采集目录默认位置不直观；希望可按个人偏好归档，未指定时放在运行文件同级目录，并将精度/性能整理成表格。

- 日志、各级 IR、ELF、性能 CSV、仿真流水、wheel 和源码快照可能分布在不同工作目录和缓存中。
- 目录名往往不足以表达用户、任务类型、环境、输入、物理卡和基线/候选关系；多人交接时需要重新翻聊天记录。
- **[待核实风险]** 同名输出覆盖、读取到旧缓存、只保留最终表格却丢失原始样本，或将不同环境的结果混在一起。
- 失败、超时和取消也需要归档；缺少文件应有明确记录，不能让“归档完成”暗示“任务成功”。

### P08：任务状态与终端、容器和会话混在一起

- **[待核实风险]** SSH 断开或 Agent 对话结束后，用户不清楚任务是否仍在执行，容易重新提交。
- 本地命令超时、Docker 客户端退出，不一定表示容器内的进程已经退出；取消请求也不等于资源已经清退。
- **[历史记录]** 既有演练出现过 Docker create 超时后对象延迟创建的情况，说明操作响应和真实执行状态需要分别确认。
- 缺少任务 ID、执行尝试、输入和状态记录时，难区分原任务恢复、新任务重跑、旧进程残留和重复结果。
- **[待核实风险]** 服务器重启后直接把旧任务标为失败并释放资源，却遗漏实际执行端或残留状态。

### P09：错误现场分散，分析和复现依赖个人会话

**[用户反馈]** 后续希望 Agent 分析精度错误、卡死、编译错误，优化性能并解读仿真流水；这些能力当前由不同工具和工程承载。

- 仅有异常末尾或一句“卡住了”，通常缺少准确环境、输入、IR、工具调用、时间线和设备背景。
- 编译失败可能发生在 Triton、NPU-IR、LLVM 或 CCE 不同层；精度差异也可能涉及参考模型和数据格式语义，不能仅凭错误关键词归因。
- **[历史记录]** HiF8 Hybrid 溢出分析需要区分设备观测与参考模型；不能把所有差异都先定性为编译器错误。
- **[历史记录]** 某些仿真采集日志在测试通过之后出现 signal 11；流水可解析不表示整个采集任务正常结束。
- 换人、换 Agent 或换会话后，如果没有共享的事实索引，就要重新搜集现场，且容易沿用旧版本结论。

### P10：监控与自动化本身也会放大资源问题

**[用户反馈/历史记录]** 本项目早期周期监控进入租户容器执行 `df -B1 --output=size,used,avail /dev/shm`。管理员转述发现同类进程数从约 236 增至 312，约每分钟增加 4 个；后续服务器发生明显卡顿并重启。

- 反复启动探针而没有确认上一次真正退出，会将一次阻塞放大为进程堆积。这是本方案早期监控设计本身需要承担和修正的问题，不能简单归因于 zdl 用户业务负载。
- 这些进程的命令和增长趋势支持“探针累积”判断；不能据此证明整机卡顿完全由一个容器造成，也没有在本文中确定底层内核/驱动阻塞根因。
- D 态进程即使收到 SIGKILL，也可能需等待内核调用返回；命令超时不保证进程已被回收。
- 后续已移除该周期容器内 df 探测，并增加探针串行、防重入、冷却和未知状态保留。修复不等于底层阻塞根因已解决。
- **[待核实风险]** 多个个人 Agent 都做高频巡检、自动重试或健康查询，造成重复轮询和系统调用压力。

### P11：个人配置和公共执行权限的边界不清

**[用户关注]** 用户希望私有 Agent 对话、Skill、MCP 配置不被他人无条件读取，并询问只在个人目录启动 harness 是否足够。

- 隔离能力取决于 Linux UID、目录权限、容器挂载和服务授权；换一个工作目录本身不构成安全隔离，同 UID 下的不同会话也不是互不信任的用户边界。
- **[待核实风险]** 将个人 HOME、模型密钥、Docker socket 或公共管理员配置共享给多个 Agent，造成越权和敏感信息暴露。
- 如果网页、CLI 和 SSH 使用不同认证体系而说明不清，容易误用账号密码；本 Demo 曾出现将 SSH 密码用于网页独立认证、反复被要求登录的反馈。
- 没有管理员权限时，个人 Agent 也不能安全承担所有租户的强制资源管理。本文不声称已经发生私有会话或密钥泄露。

### P12：留存与清理依赖人工，空间和证据之间缺少明确规则

- **[历史记录]** 编译产物、wheel、IR、仿真数据和失败现场会持续积累；本 Demo 自身历史任务也曾达到上限，需要显式批准才从 1000 调整为 1100。这是管理工具自身的案例，不是整台服务器任务数量统计。
- **[待核实风险]** 只按文件大小或时间删除，可能清掉仍被实验引用的输入、基线或失败证据；全部保留又会耗尽空间或管理容量。
- 缓存、任务临时目录、正式归档和备份需要不同保留规则；任务完成不等于所有目录都可立即清理。
- 个人下载、共享挂载和容器卷可能包含多份副本；应用记录的额度也不等于底层文件系统硬配额。

### P13：团队缺少统一状态视图和完成通知

**[用户反馈]** 希望网页能看到哪个用户运行哪类任务、占用多少资源。

- 只有 ps、Docker 进程或设备利用率时，通常无法直接得知用户意图、等待原因、预估资源和结果位置。
- **[待核实风险]** 用户需要反复登录查看长编译/仿真是否完成；失败、资源压力或需要人工处理的情况没有及时送达本人。
- 公共状态应有可见范围，不能为了展示“谁在运行什么”就公开私人源码路径、完整命令参数、日志或对话。
- 直接运行的旧任务与统一入口提交的任务需要明确区分；网页能看到部分占用，不代表拥有完整任务语义或控制权。

### P14：公共回归和问题 PR 归因重复消耗资源

**[用户反馈]** triton-ascend 每天合入 PR 后，可能需要排查引入问题的 PR，反复构建 wheel、测试并提出 revert 或修改建议。

- 缺少固定基线、测试输入、环境和失败记录时，难区分新回归与既有失败。
- **[待核实风险]** 多人重复构建相同版本，公共回归与个人前台任务抢资源，排查结果散落在聊天记录中。
- 此项作为后续公共项目保留，当前没有启用凌晨自动任务，也不意味着 Agent 获得修改公共分支或自动 revert 的授权。
